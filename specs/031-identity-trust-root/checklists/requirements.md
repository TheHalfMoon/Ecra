# ECR-031 Requirements Quality Checklist

**Purpose:** pre-implementation quality gate for Identity, Trust Root & Sensitive Storage Foundations.  
**Pass:** 2 after Pass-1 C1–C4 remediation.  
**Rule:** every item must be `[x]` before `TASKS_READY`; checklist success does not itself authorize implementation.

## Scope and ownership

- [x] ECR-031 purpose is bounded to identity assertions, local enrollment/bootstrap, actor/principal/on-behalf-of binding, trust root, key lifecycle, protected trust state, protected local storage and protected authenticity anchors.
- [x] ECR-003 owns general authorization/declassification/approval/secret-use mediation.
- [x] ECR-004 owns independent action outcome verification/reconciliation.
- [x] ECR-016 owns protocol authentication/token mapping; no token passthrough is ambient authority here.
- [x] ECR-021 local-model gateway is not pulled forward.
- [x] ECR-022/ECR-029 cross-device sync/recovery/export are excluded.
- [x] ECR-001 Actor/Principal/IdentityAssertion IDs and references are reused rather than replaced.

## Local bootstrap / enrollment — C1

- [x] First bootstrap creates an opaque **Ecra-local installation principal**, not a claim of legal/external human identity proofing.
- [x] PrincipalId/TrustRootId/enrollment IDs are generated from approved randomness; OS username/email/display label cannot become canonical PrincipalId.
- [x] OS user/session context selects the reachable native keystore only; it is not identity proof.
- [x] Bootstrap is complete only after protected backend secret creation + authenticated trust-state durable publication + authenticated reopen.
- [x] Orphan backend material after crash yields `incomplete_bootstrap`; no silent second identity/root mint.
- [x] `EnrolledPrincipalHandle` is obtainable only from authenticated local enrollment/trust state.
- [x] No NIST IAL/AAL/FAL certification or external identity-proofing claim is made.

## Identity semantics and issuance — C3

- [x] Actor attribution is explicitly non-authenticating.
- [x] Existence of `IdentityAssertionRef` is explicitly non-validating.
- [x] Assertion subject, actor, issuer, signing key, audience and validity are exact typed fields.
- [x] On-behalf-of binding is explicit and missing never means ANY/unrestricted.
- [x] Validation context includes explicit evaluation time and expected relying context.
- [x] Replay semantics are explicit where single-use assertions apply.
- [x] `ValidatedIdentityContext` is defined without capability/approval/authorization semantics.
- [x] Labels/usernames/emails/paths/protocol strings cannot become canonical principal identity.
- [x] No generic `issue(arbitrary_principal_id, ...)` production API exists.
- [x] Assertion issuance requires `EnrolledPrincipalHandle` + current `VerifiedTrustSnapshot` -> non-serializable `IssuerSession`.
- [x] Caller can request actor/audience binding but cannot replace the session subject principal.
- [x] V1 on-behalf-of issuance cannot mint another arbitrary principal.
- [x] No ECR-031 IPC/network assertion-minting service exists.

## Authoritative lifecycle / rollback — C2

- [x] Security-critical enrollment/current-generation/retirement/revocation state is stored in authenticated `ProtectedTrustStateV1`.
- [x] Ordinary DB/filesystem metadata is rebuildable/non-authoritative and cannot activate/unrevoke a key.
- [x] `VerifiedTrustSnapshot` is created only after native backend open + protected-state authentication + lifecycle invariant validation.
- [x] Pure validator/issuer accepts `VerifiedTrustSnapshot`, not raw unsigned metadata.
- [x] Every lifecycle mutation atomically publishes a new authenticated protected trust state.
- [x] `state_generation` is not marketed as a hardware monotonic counter.
- [x] V1 does not claim universal rollback resistance against restoration of an older valid protected state plus equivalent authorized OS trust-store state.
- [x] Stale/unsigned/replaced metadata negative tests are named in tasks/quickstart.

## Cryptographic contract / custody — C4

- [x] Signed payload canonicalization is explicit and domain-separated.
- [x] Assertion digest is type/domain distinct from existing generic/action/ledger digests.
- [x] V1 assertion/protected-anchor signing algorithm is frozen to Ed25519.
- [x] Ed25519 software seed/key is generated by production CSPRNG and stored only under native backend protection.
- [x] Software signing material may be opened only for bounded use in a redacted/zeroizing wrapper.
- [x] Portable v1 path explicitly does **not** claim Secure Enclave/hardware-backed/non-exportable signing.
- [x] Future native non-exportable signing requires a versioned algorithm-suite extension and separate evidence.
- [x] Protected-envelope AEAD algorithm, key size, nonce size and full-tag requirement are explicit.
- [x] Interpretation-critical envelope metadata is authenticated as AAD.
- [x] Nonce uniqueness ownership is explicit.
- [x] HKDF is domain-separated over native-backend-protected master material for bounded process use.
- [x] Protected anchor is distinct from `LedgerDigest` and `VerificationReceipt`.
- [x] Unsupported algorithms/versions fail closed.

## Key lifecycle

- [x] Key purpose and key status are typed and distinct.
- [x] One active key per trust-root/purpose invariant is explicit in verified protected state.
- [x] Rotation, retirement and revocation semantics are distinct.
- [x] Revocation is not conflated with destruction/unavailability.
- [x] Retired keys cannot create new material.
- [x] Current assertion validation rejects revoked assertion-signing keys.
- [x] Generic public raw private/root key export is excluded from trusted v1 API.

## Native backend and platform honesty

- [x] Production backend unavailable/locked/unsupported fails closed.
- [x] Plaintext/file/environment/process-memory fallback is prohibited.
- [x] Test backend is unreachable through ordinary production configuration.
- [x] Common backend capability metadata cannot overstate platform guarantees.
- [x] macOS Data Protection Keychain is the v1 native acceptance baseline.
- [x] Portable Ed25519 signing on macOS is described as Keychain-protected software signing, not Secure Enclave signing.
- [x] Windows default DPAPI is not described as cross-machine protection.
- [x] Linux Secret Service 0.2 is labeled DRAFT.
- [x] Linux lookup attributes are non-secret and prohibited from carrying sensitive values.
- [x] Windows/Linux are not marked verified without native evidence.

## Secrets, privacy and persistence

- [x] Raw private/root/derived key bytes are excluded from ordinary serializable key metadata.
- [x] Sensitive plaintext and keys are excluded from Debug/Display/log/error/run-artifact paths.
- [x] At-rest synthetic sentinel scan is an acceptance criterion.
- [x] ECR-031 protected envelope is not blanket authorization for other slices to persist sensitive data.
- [x] Real disclosure/remote egress remains gated by ECR-003.
- [x] No hidden telemetry/cloud requirement is introduced.
- [x] Cross-device recovery and team governance are excluded from v1.

- [x] ambient assertion mint is addressed.

## Bounded input/execution

- [x] strict assertion/trust-state/envelope byte/depth/count limits are specified.
- [x] arbitrary recursive delegation/certificate chains are excluded from v1.
- [x] parser validation precedes expensive cryptography/materialization where practical.
- [x] no recursive model/tool/process loop exists in this slice.
